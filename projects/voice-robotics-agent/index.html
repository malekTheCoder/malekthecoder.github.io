Overview

You speak a natural language command like "stack the red cube on top of the blue cylinder" or "arrange all objects in a line", and a Franka Panda arm carries it out in real time in the MuJoCo physics simulation.

The system transcribes what I said, the model breaks the request into an ordered list of sub-goals, and the arm executes them one at a time. Gravity, collisions and contact forces are live, so things genuinely go wrong: a grip slips, a stack topples, an object ends up somewhere unintended. When that happens the agent notices, works out why, and plans a new route to the same goal.

Before it reports success, a second independent model call compares the live scene against the intended arrangement and rejects false completions.

Commands it handles:

  • Pick and place to a named location or exact coordinates
  • Stacking, including order-specific requests like "reverse the stack"
  • Spatial arrangements, lines, rows, corners, grids
  • Relative instructions like "move it to the other side" or "put it next to the cylinder"
  • Multi-object tasks like "move all cylinders to the left"

How it works

Five stages with a loop in the middle: the agent cycles between acting and checking until the scene matches the request, or it decides the task can't be done.

Two model roles do the thinking. One handles task decomposition and goal verification; the other decides the next action at every step.

Voice runs through Deepgram (Nova-3 for speech-to-text, Aura-2 for text-to-speech) when a key is present, and falls back to faster-whisper and pyttsx3 locally when it isn't.

Planning and decomposition

The agent's behaviour at every step comes down to one system prompt: the actions it can call, the coordinate system and reachable workspace, pre-computed coordinates for lines, rows and grids so it never guesses, and a strict JSON output format so every step is parseable.

  • Available actions, pick, place, move, open/close gripper, wait, report success/partial/failure, and ask the user a clarifying question
  • Coordinate system, axes and reachable workspace bounds, so the agent never targets a position the arm physically cannot reach
  • Table placement rules, how to interpret "left side", "the other side", "across the table"
  • Pre-computed arrangements, exact safe coordinates for lines, rows, corners, and grids, so the agent looks them up instead of guessing
  • Anti-oscillation, stops the agent picking up an object it just placed and putting it back
  • Strict output format, every response must be {"reasoning", "action", "parameters"} so each step is machine-parseable

Anti-oscillation is in there too. The agent would place a cube correctly, look at the scene again, decide the cube was in the wrong spot, and move it back. This used to be one of the most common failures.

When a plan fails

In a real physics simulation, plans fail. The gripper closes a fraction too early, a stack tips, an object slides out of reach.

  • Classifier, decides what kind of failure just happened. A dropped object and an unreachable target need different responses.
  • Handler, produces a new plan given that classification, or concludes the task genuinely cannot be completed.
  • Verifier, the independent check that runs before any success is reported.

The verifier is the piece I'd defend hardest. It's a separate LLM call that gets the serialized scene and the original request, and it rejects completions that don't match.

When it fails, the agent replans from the current scene rather than retrying the same action.

It can also report a task as impossible instead of looping until something times out.

Motion and collisions

Arm motion uses inverse kinematics via mink, backed by the daqp solver: given a target pose for the gripper, IK works out the joint angles that put it there.

Problem: the solver is position only and not collision aware. It will happily drive the arm straight through a stack of cubes to reach a target.

Solution: every motion routes through a transit arc instead of driving straight at the target. 

lift straight up  →  travel at a safe height  →  descend onto target

A TRANSIT_Z_MAX ceiling and an APPROACH_CAP_Z floor stop the wrist tilting on tall stacks, and a descent orientation lock stops cylinders spinning as they are placed. It is a constraint rather than a real fix: the arc is conservative and sometimes takes a longer path than it needs to.

The web portal

A FastAPI portal streams the simulation as MJPEG at about 30 fps, with a WebSocket carrying state.

You can add and remove objects mid-session, pick a layout, watch the reasoning trace, and export session logs.
